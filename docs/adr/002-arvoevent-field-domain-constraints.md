# ADR-002: ArvoEvent Field Domain Constraints

- **Status:** Accepted
- **Date:** 2026-08-03
- **Scope:** Arvo ecosystem
- **Supersedes in part:** ADR-001 — `source` and `dataschema` format; string-field character domain; `executionunits` number domain

Conformance language is as defined in [ADR-000](./000-arvo-system-identity-and-architectural-principles.md).

## Scope

This ADR narrows four rules within [ADR-001](./001-arvoevent-structure.md)'s Structural Validity section. Every other ADR-001 rule — the eighteen-field set, their types, defaults, remaining structural-validity rules, and propagation — is unchanged and remains governed by ADR-001 directly.

It changes:

- `source`'s format, from unconstrained to a non-empty RFC 3986 URI-reference.
- `dataschema`'s format, similarly constrained to a non-empty RFC 3986 URI-reference — ADR-001 left it unaddressed rather than explicitly unconstrained, but the effect is the same.
- Every ArvoEvent string field's character domain, excluding control characters, Unicode noncharacters, and unpaired surrogates.
- `executionunits`' number domain, from any finite number to finite IEEE 754 binary64.

It does not touch `data` or `baggage`'s content, `depth`, contract validation, or any field's semantics — only the shape of the values these four rules already govern.

## Context

ADR-000 requires that every ArvoEvent be transformable into a CloudEvent. Working out what that transformation requires revealed that ArvoEvent's own definition permits values no CloudEvents-conformant transformation could represent: CloudEvents types `source` as a URI-reference, `dataschema` as the stricter, absolute URI, and every other context or extension attribute value as a narrower `String` domain excluding control characters and Unicode noncharacters, and has no attribute type for an arbitrary-precision or unbounded number. ADR-001 constrained none of this.

Two responses were available: absorb the gap into the transformation layer specifically, via a reversible encoding applied only at the ArvoEvent-CloudEvent boundary, or close it in ArvoEvent's own definition. This ADR takes the second path. Each rule still has its own justification independent of CloudEvents, even though — as the next paragraph explains — the exact boundary each rule draws is now stated by reference to CloudEvents' type system rather than enumerated independently. A control character or unpaired UTF-16 surrogate embedded in an identifier-like field — `type`, `category`, `executionid` — is virtually never a deliberate choice, and far more often a sign of a bug or corrupted input than a legitimate value. A URI-reference is a well-understood, general-purpose identifier shape that the overwhelming majority of existing `source` and `dataschema` values already satisfy without any change, and imposes nothing that "the convention a deployment adopts" — ADR-001's own phrase — could not just as easily have adopted anyway. And a fixed, well-known numeric domain is what makes a value portable across independently implemented consumers at all; an unbounded, language-neutral domain either requires every implementation to support arbitrary precision or silently degrades to whatever precision each one happens to use, which is not really a shared domain.

The rules below are ArvoEvent's own domain constraints, not a description of how any particular CloudEvent transformation happens to work — but they are defined by reference to CloudEvents' own attribute type system, pinned specifically to [CloudEvents 1.0.2](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md), rather than by an independent enumeration, because that type system is precise and already exactly the boundary every affected field needs to satisfy toward the transformability ADR-000 requires. The trade is named here rather than left implicit: this ADR's boundary is fixed to what CloudEvents 1.0.2 specifically says `String` and `URI-reference` mean, not to whatever a future CloudEvents version might say instead. An accepted ADR's meaning does not move because an external specification changes out from under it — a later CloudEvents version altering those type definitions has no effect here unless a superseding ADR adopts it, the same discipline that governs any other change to this ADR. A serialization target with a different, incompatible type system would need its own ADR to narrow the same or additional fields further; this one does not attempt to anticipate what that would require.

`arvo-core` v4 has not been declared stable, and ADR-000 states explicitly that compatibility guarantees are deferred until it is: "compatibility guarantees for stable APIs, event representations, contracts, persisted state, and adapter interfaces will be defined before it is declared stable." This tightening is exactly the kind of pre-stability correction that window exists for.

## Decision

**Superseded: string and identifier domains, by reference to CloudEvents' attribute type system.** ADR-001 states `source`'s format as unconstrained, leaves `dataschema`'s format unaddressed, and places no character restriction on any other string field. All of this is superseded. Every ArvoEvent field held to the CloudEvents `String` domain below MUST satisfy it — as [CloudEvents 1.0.2](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md) defines it, pinned to that version specifically — which excludes the control-character ranges U+0000–U+001F and U+007F–U+009F, Unicode noncharacters (U+FDD0–U+FDEF and the last two code points of any plane), and unpaired UTF-16 surrogates (a code unit in U+D800–U+DFFF with no matching pair). Where this ADR holds a field to an RFC 3986 URI-reference domain, that value MUST additionally satisfy [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986)'s URI-reference grammar, in exactly the canonical form [RFC 3986 §6.2.2](https://www.rfc-editor.org/rfc/rfc3986#section-6.2.2) ("Syntax-Based Normalization") defines: the scheme and host, if present, lowercase; every percent-encoded octet's hex digits uppercase; every percent-encoded octet that corresponds to an unreserved character decoded rather than left encoded; and the path free of any `.` or `..` segment the `remove_dot_segments` algorithm (§5.2.4) would otherwise resolve away. A value satisfying the grammar but not already in this form MUST be rejected, so that this domain never admits two differently-spelled values a consumer would otherwise have to normalize before treating as the same reference. [RFC 3986 §6.2.3](https://www.rfc-editor.org/rfc/rfc3986#section-6.2.3) ("Scheme-Based Normalization") — removing a scheme's own registered default port, for instance — is explicitly out of scope: RFC 3986 itself states this class of normalization is optional and specific to each scheme, not a property every URI-reference shares, and this ADR imposes none of it. The affected ArvoEvent fields are:

- Native CloudEvents `String`: `id`, `type`, and `subject`.
- CloudEvents' established Distributed Tracing Extension: `traceparent` and `tracestate`, carried under those exact attribute names by a convention external to Arvo; nullable values are subject to this rule only when non-null.
- ArvoEvent's own string fields, with no CloudEvents-native attribute and no established extension convention: `parentid`, `initid`, `executionid`, `category`, `to`, and `domain`. This ADR holds them to the CloudEvents `String` domain on the independent grounds given above, without taking a position on whether a future transformation ever carries them as a CloudEvents extension, places them elsewhere, or does something else entirely; nullable values are subject to this rule only when non-null.
- RFC 3986 URI-reference: `source` and `dataschema`. Only `source` directly matches the corresponding CloudEvents attribute type — `dataschema`'s own CloudEvents type is the stricter, absolute `URI`; see **Source and dataschema** below for why this ADR holds it to `URI-reference` instead.
- CloudEvents `Timestamp`: `time`, already constrained to RFC 3339 by ADR-001; no new rule applies.

Two fields are deliberately absent from every list above. `depth` needs no new rule at all: ADR-001 already limits it to a non-negative integer, and an integer of any size has an exact, unambiguous decimal string form without narrowing its domain. `executionunits` does get a new rule — stated on its own terms below, not here — because that rule is a numeric domain, not a CloudEvents attribute-type domain: binary64 is not part of CloudEvents' type system, and nothing in this ADR presumes which CloudEvents attribute, if any, eventually carries it.

Nullability and every other field-specific semantic rule from ADR-001 remain unchanged. Strings nested in `data` or `baggage` remain governed by ADR-001's JSON-value domain rather than this restriction.

**Source and dataschema.** `source` and `dataschema` remain ordinary strings in every language API. A URI-reference is an identifier, not necessarily a URL and not necessarily dereferenceable; familiar service identifiers such as `order-service`, hierarchical paths such as `api/users`, and fragment-only contract references such as `#/contracts/user` are all valid relative references, and the overwhelming majority of existing `source` and `dataschema` values already satisfy the domain without any change. A producer whose natural identifier is not already URI-reference-shaped — containing whitespace or a raw non-ASCII byte sequence, for instance — MUST percent-encode the offending octets before constructing the ArvoEvent; this ADR does not perform that encoding automatically, so a constructed value is always exactly the string its producer chose. The same principle extends to canonical form as RFC 3986 §6.2.2 defines it: a scheme or host in the wrong case, a percent-encoded octet with lowercase hex digits or one unnecessarily encoding an unreserved character, or a path segment left unresolved, is grammatically valid but MUST still be rejected, since two different spellings of what the grammar considers the same reference would otherwise both construct successfully — undermining exactly the stable, comparable identifier this rule exists to guarantee. A producer whose identifier is not already in this form MUST canonicalize it before constructing the ArvoEvent, the same obligation percent-encoding already places on non-ASCII or whitespace-bearing input. Scheme-based normalization (RFC 3986 §6.2.3) — a scheme's own default port, for instance — is not part of this requirement, since RFC 3986 itself makes that class optional and scheme-specific rather than a property every URI-reference shares; an implementation is not required to reject a value solely for carrying an explicit default port. CloudEvents itself types `dataschema` as the stricter, absolute `URI` rather than `URI-reference`; this ADR deliberately holds `dataschema` only to the same URI-reference requirement as `source`, since nothing here depends on the stricter form and it would break the fragment-only contract references already in use.

**Execution units.** `executionunits`, when non-null, MUST be a finite IEEE 754 binary64 value. This is a numeric domain, not a CloudEvents attribute-type domain: binary64 is a general, widely implemented standard for representing a finite real number exactly and portably, chosen because ADR-001's original domain — any finite number, unconstrained in magnitude or precision — has no canonical representation at all, in any format, until some concrete numeric domain is fixed. Fixing the domain is a prerequisite for a deterministic, lossless encoding to exist; it does not by itself supply that encoding, or say where an encoded value is carried on a CloudEvent — both are left entirely to whichever ADR defines that transformation. Its sign remains unconstrained and Arvo still assigns it no meaning; only its representable range and precision narrow. A value of `-0` is normalized to `0` at construction, so ArvoEvent itself never distinguishes them. Numbers nested in `data` or `baggage` are unaffected and retain ADR-001's existing JSON-number domain.

**Enforcement.** All of the above is structural validity in ADR-001's own sense: checked at construction, checked identically wherever an event enters as data, and requiring no contract, store, or other event to evaluate. No new validation pathway is introduced; every rule here extends the one ADR-001 already defines.

## Consequences

**Gained.** Every ArvoEvent field affected by these rules now inhabits a fixed, well-specified domain regardless of which wire format or language implementation handles it — narrower than JSON in general, but exactly the shape a value needs to be portable across independently implemented consumers rather than merely valid within one runtime's own type system. `source`, `dataschema`, and every other string field this ADR narrows now satisfy CloudEvents' own `String` or `URI-reference` domain outright, with no encoding step and no possibility of failure — regardless of which CloudEvents attribute, if any, eventually carries them. `executionunits` is different: no CloudEvents numeric type holds a fractional or out-of-32-bit-range value, so an encoding step is still required regardless of this ADR — what this ADR contributes is that a deterministic, lossless encoding becomes *possible* at all, since a fixed domain (finite binary64) is a prerequisite for any canonical representation to exist, where ADR-001's original unbounded domain had none. This removes the field-domain obstacles to fulfilling the transformability ADR-000 requires, and the domain is stated completely enough, by reference to CloudEvents' own type system, that any serialization target sharing that type system inherits it without renegotiation; one that does not would need its own ADR to narrow further. Rejecting an out-of-domain value at construction also surfaces what was previously silent, likely-accidental input as an immediate, diagnosable error, consistent with the Diagnostic Quality ADR-001 already holds every other rule to.

**Paid for.** This is the first breaking change to an ADR-001 structural rule since it was accepted. A producer supplying a `source` or `dataschema` outside URI-reference syntax, a string field containing a control character or unpaired surrogate, an `executionunits` value outside finite binary64, or a `source`/`dataschema` that is grammatically valid but not already in §6.2.2 canonical form (a differently-cased scheme or host, non-canonical percent-encoding, an unresolved dot-segment) — all of which previously constructed successfully — now fails, and a stored `executionunits` of `-0` is now silently normalized to `0`. ADR-000's stated pre-stability allowance for `arvo-core` v4 is what makes this an acceptable cost now rather than a compatibility break requiring its own migration story.

## Considered Alternatives

**Absorbing these constraints into a CloudEvents transformation layer instead of tightening ADR-001** — considered, not chosen. It would have kept ADR-001 untouched and avoided any breaking change to ArvoEvent's own construction rules, at the cost of every affected field needing a reversible encoding transform, a `source` or `dataschema` that is not always the literal value its producer wrote once carried on the wire, and the same problem needing to be solved again — potentially differently — by any future non-CloudEvents serialization target. Narrowing the domain once, in ArvoEvent's own definition, is a one-time, pre-stability cost against a permanent, general-purpose encoding mechanism every future consumer would otherwise need to either reuse or reinvent.

**Holding `dataschema` to CloudEvents' stricter, absolute `URI` type rather than `URI-reference`** — considered, not chosen. It would match CloudEvents' own typing exactly, but a fragment-only contract reference such as `#/contracts/user` — already in use — is a valid URI-reference and not a valid absolute URI, since it carries no scheme. Nothing in this ADR depends on the stricter form, so `dataschema` is held to the same requirement as `source` rather than breaking an existing, working convention for a distinction with no consumer here.

**Preserving ADR-001's unbounded `executionunits` number domain** — considered, not chosen. A lossless, cross-language canonical representation for an unbounded, language-neutral number would require Arvo to first define an arbitrary-precision numeric model and then require every implementation to support it, just to exchange an opaque accounting value. Finite binary64 matches Arvo's TypeScript-first runtime and is already implemented natively or near-natively across essentially every target language, making a deterministic encoding possible without Arvo inventing a numeric model of its own. Which specific encoding is actually used, and where it is carried on a CloudEvent, is left entirely to whichever ADR defines a transformation that needs one.

**Enumerating the excluded code points directly in ArvoEvent's own terms, citing no external specification at all** — considered, not chosen. Citing CloudEvents' type system instead was chosen for precision, not for automatic generalization to future fields: this ADR enumerates every affected field explicitly, `time` and `depth` included as fields needing no new rule rather than passed over in silence. For `id`, `type`, `subject`, `traceparent`, `tracestate`, and `source`, the citation states a domain CloudEvents itself already defines for that field. For the remaining Arvo-only strings and for `dataschema` — which deliberately diverges from its actual CloudEvents type — the citation borrows the same precise, already-versioned boundary because it already exists, not because CloudEvents assigns these fields a type of its own. The reference is pinned to CloudEvents 1.0.2 specifically, not to whatever CloudEvents says at any given time, and the exact code points are already spelled out in this ADR's own text above — so this ADR's meaning does not move if a future CloudEvents version changes its own type definitions, and adopting such a change here would need a superseding ADR, the same as any other change.

## Conformance to ADR-000 and ADR-001

**Effect on ADR-001.** This ADR supersedes exactly four things in ADR-001's Structural Validity section: the sentence stating `source`'s format is unconstrained; the absence of any equivalent format constraint on `dataschema`; the absence of any character restriction on string-valued fields; and the unbounded finite-number domain for `executionunits`. Every other rule ADR-001 states — the eighteen-field set, their types, defaults, propagation, and every other structural-validity rule — is unchanged and remains governed by ADR-001 directly.

**Invariants depended on.** *Explicit Contracts and Runtime Validation* — these remain construction-time, runtime-checked rules, not compile-time ones. *Observability by Default* — a well-formed `source`, a well-formed `dataschema`, and control-character-free identifiers are what let routing, correlation, contract-resolution, and tracing tooling treat these fields as stable identifiers rather than arbitrary blobs.

**Invariants strained.** None.

**Required of infrastructure adapters.** None beyond what ADR-001 already requires — this ADR changes what ArvoEvent permits at construction, not what an adapter carries.

**Left deferred.** Whether any further ArvoEvent field deserves a narrower domain than ADR-001 originally gave it is not addressed here; this ADR closes only the specific gaps a CloudEvents-conformant transformation of ArvoEvent requires.
